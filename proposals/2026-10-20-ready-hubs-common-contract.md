# Common contract for the three ready-made hub proposals

Status: Draft for founder approval. Date: 20 October 2026. This is a supporting part of the three hub proposals, not approval to implement, deploy, publish, spend or contact anyone.

## Problem

The three hubs have useful workflows, but a builder must still connect setup instructions, runtime settings, company context, permissions and provider behavior. The same knowledge must not become three independently edited copies for chat, workflows and MCP. A working synthetic demonstration does not establish a useful first result on the builder's own material or dependable team operation.

## Why now

The founder has supplied seven Hubzoid 2.0 priorities, in this order. These guide tradeoffs within all three proposals. They do not turn every platform roadmap item into a hub deliverable.

| Priority | Required behavior and acceptance evidence |
|---|---|
| 1. One brain across chat, workflows and MCP | One maintained context source and domain service per hub. All surfaces receive the same domain decisions, permission checks, rule/source revision identifiers and evidence references. Hub instructions, skills and style govern execution where Hubzoid runs the agent, including MCP tools that delegate to it. An external MCP client's own generation is outside that guarantee. Live retrieval records policy revisions and evidence identifiers rather than promising identical search results. |
| 2. An agent is a folder | Instructions, skills, configuration, tools, connector definitions, source references, examples and setup recipe are inspectable files. A fresh copy can be reproduced using those files, declared credentials and a tested SDK. No essential configuration exists only in a UI. |
| 3. Make it your own | Document file-based choices for supported models, harnesses, station definitions, connectors, knowledge, workflow defaults, appearance and access. Mark configurable behavior separately from extensions requiring code. Keep the one Hubzoid web app, customizable through its supported theme/layout settings, and existing tool interfaces/MCP. |
| 4. Value visible quickly | One clearly stated job, one labelled sample, then one useful result on the builder's material and one saved correction that changes the next result. Measure cold install, connection, bootstrap and task time separately. |
| 5. Production quality | Every advertised state, action, route and in-scope page works. Empty, loading, errors, permission denial, retry, cancellation and recovery have finished behavior. Synthetic data is labelled. No dummy controls, broken links or placeholder qualification jobs count as complete. |
| 6. Claude-led setup | Claude Code can configure, validate, start and operate the documented path through files, CLI and API without manual Hubzoid UI configuration. Cowork uses the same contract through capabilities verified in its environment. A capability check gives a precise supported handoff when a terminal, file or authenticated API capability is unavailable. |
| 7. Explicit enterprise access | Authorize every tool and consequential action against the verified principal and the hub, source/customer/repository/case scope it affects. Apply the same decision in chat, workflows, MCP, CLI and direct API. Test revocation and indirect artifact access. |

## What should happen

### Canonical context and execution

The existing hub folder is the maintained source for instructions, approved rules, styles, skills and connector definitions. Operational records, conversation history, retrieved documents and secrets retain their own storage and access rules. Setup conversation becomes shared knowledge only when an explicit reviewed file change is activated.

Every surface calls the same domain services and permission checks. Each run/result records applicable context and rule revisions, evidence references and actor. Raw MCP tools expose those services and authorized evidence. Delegated MCP execution also runs the hub agent. Connecting an external assistant does not transfer control of its system prompt to Hubzoid.

Before dispatch, recompute a proposed business action using current rule/source revisions and provider state, and recheck current authority. If its canonical digest differs from the approved digest, the approval is void and a fresh preview and approval are required. An unchanged digest records both revisions. This defines a material action change. Lost authority always blocks, even if the digest is unchanged. Preserve prior evidence rather than silently continuing an outdated plan.

A correction originating in chat, a helpdesk or MCP becomes a proposed-change record in the SDK data root, citing the case, evidence and intended file diff. A verified authorized person activates the exact diff through the supported file-update mechanism. Read-only source uses the qualified builder/update workspace. Pre-shipped chat tools still write only within `<hub>/output/<session>/`. If the SDK lacks proposal storage or authorized revision activation, a narrowly scoped SDK proposal is a named prerequisite. This remains an ordinary reviewed Hub edit, not a new memory platform.

A company may supply an explicitly shared foundation to several hubs. Use existing supported knowledge/MCP source capabilities where they meet the need. Name one authority and revision for shared rules, preserve source authorization, and avoid separate editable copies. A file reader must not escape the hub root through a path or symlink. Cross-hub access goes through a scoped authorized capability. This proposal does not select a new global memory system or require all company data in one model prompt.

### Claude-led setup contract

Each hub owns a builder recipe plus equivalent human-readable instructions. Prefer existing SDK commands, file validation and native provider connectors over a new setup framework. Any new CLI/API operation named during implementation must be documented as proposed until shipped and tested.

The recipe must:

1. Discover OS, Python, SDK revision, available runtime, parser/sandbox needs and already configured providers. Read safe metadata only. Return structured status and concrete recovery instructions.
2. Explain the job and choose an approved source/repository/mailbox/helpdesk, company scope and selected representative material. Preserve originals and label synthetic material.
3. Prepare a setup preview: installation/runtime choices, connector permissions, planned file changes, proposed mappings/rules, retained data and expected effects. Show the focused diff and unresolved assumptions.
4. Let the person authenticate or supply a credential reference using the supported secure entry mechanism. Never collect raw secrets in chat, logs, proposals or Git. Reuse authorized credentials where appropriate.
5. Apply configuration with expected revisions and idempotency guards within delegated setup authority. Request a separate human confirmation for protected activation or access changes. Record progress in the SDK-managed data directory and resume safely after interruption. A repeated setup must neither duplicate connections/imports nor overwrite user edits.
6. Run one read/preview task on the user's material, show the evidence and unresolved questions, then save and verify one correction. Offer a supported write/draft only after the selected mode and principal are authorized.
7. Propose a teammate's scoped access as a reviewable file/CLI/API change, obtain the authorized administrator's separate confirmation, prove allowed and forbidden actions, and provide restart, backup and upgrade instructions.

No manual Hubzoid setup UI is required. Fresh provider sign-in/MFA/consent, provider terms, account ownership and exact consequential approvals remain verified human acts. The assistant presents the appropriate external consent or secure-entry handoff and resumes afterward. Pre-authorized delegated credentials permit unattended setup only within their granted scope where the provider supports it. The assistant must not impersonate a person, approve its own action or bypass provider consent.

Use a scoped delegated setup identity. It may prepare files and activate already authorized connector definitions. It cannot mint or widen grants, read or administer secret values, activate a shared context revision, or approve business actions. Protected acts use the SDK's authenticated human confirmation handoff through a separate, non-delegated principal session. Bind confirmation to principal, action/resource, exact digest and time. The delegated setup/runtime credential cannot produce that confirmation. Reuse existing identity and approval facilities. If this separation is absent, it is a must-have SDK dependency before the path is promoted. A confirmation is an identity/approval act, not manual Hubzoid configuration. Ordinary local host ownership is a trust boundary, not a claim that Hubzoid can restrain a hostile machine administrator.

For email, helpdesk, GitHub-event and scheduled work, the initiator is distinct from the approver. A verified internal principal with the action/resource approval grant approves consequential work. External senders and service identities cannot approve. A personal owner may approve their own proposed change or action through that human handoff. No mandatory second person is introduced. Enterprise separation of duties may further restrict eligible approvers.

Claude Code and Cowork are both required setup acceptance targets. Qualify their paths separately, using supported file/CLI/API access or an existing authorized bridge. If Cowork cannot complete the proposed path, return that capability gap for a founder decision rather than quietly completing only Claude Code or adding a second chat/runtime product. Cowork is an authoring/setup surface, not a new runtime adapter or a second Hubzoid chat interface. Preserve the existing Codex authoring path and qualify each hub on Claude-only and Codex-only execution installations. Do not require both subscriptions or a second vendor for review. Default monetary budgets remain opt-in, with visible cost estimates and configurable bounded task/retrieval behavior. Local first use should reuse the installed runtime's existing supported sign-in without requiring API spend. Unattended intake, schedules, hosted and teammate-shared operation record the authentication type for the exact qualified row. A local login or one founder-tested token does not prove every other combination. No new vendor subscription is required, and paid fallback credentials are never enabled silently.

### Customization and access

| Area | Files and behavior | Who may activate |
|---|---|---|
| Knowledge, policy, mappings and examples | Explicit sources and reviewed diffs. Explain typed supported options and code extension points. | Hub/context manager within allowed source scope. |
| Model, harness and station choices | Runtime-neutral domain contracts, same tool names/schemas/outputs. Configured model changes invalidate affected station/context revisions. | Builder/admin with runtime permission. |
| Connectors and secrets | File definitions contain references, scopes and capabilities. SDK secret store or declared operator source holds values. | Credential administrator for credential changes, connector manager for activation. |
| Tools and business actions | Explicit per-tool/action grants and resource scopes. External content cannot grant authority. | Authorized administrator grants. A verified internal principal holding the action/resource approval grant confirms exact content. |
| Appearance and working surface | Existing Hubzoid web app theme/layout and native helpdesk/repository outputs. CLI/API equivalent for each advertised setting. | Appearance/admin grant. |

The capability inventory names one authority for every setting. File-authoritative items are instructions, rules, mappings, tool/action policies, role grant bundles, connector definitions and supported appearance settings. Changes produce a reviewed revision. Console/CLI/API editing of these items produces that revision through the same activation path. Runtime-authoritative items are verified identities, account links, member-to-role assignments, secret values, approvals and per-user state. These stay in the SDK store, with scoped CLI/API inspection and export where appropriate, secret references rather than secret-value export, and operational backups. No item has two writable authorities. Existing installations need an explicit additive mapping/migration if current storage differs. A file role bundle alone never creates an authenticated member or assignment.

Maintain a versioned capability inventory for every exposed tool and action: name/schema, read/write classification, required grants, resource/source scope, caller identity, action mode, required approver and protected output/artifact access. Generated tests exercise allowed and denied calls against that inventory so a newly registered tool cannot inherit unrestricted access. Use the SDK's access and operation systems. Generic member privileges do not imply secret administration, arbitrary tool execution or source access. Generated tools and user code receive no extra privilege merely because they live in the folder. File policy changes require an authorized versioned diff. Runtime membership and identity changes require an authorized SDK operation. Neither is authorized by a setup prompt. Requests carry verified initiator identity and the eligible internal approver separately through queued work. Recheck current access at dispatch and read time, including restored/retrieved content and direct artifact URLs. Work waiting for an approval respects revocation, changed recipients and changed content.

Keep context-change approval separate from business-action approval. Preserve `off`, `draft` and `approve` action modes. A provider draft is a real unsent provider object or an explicitly qualified native-editor experience. A private note or generated preview must not be labelled a native draft. No automatic customer sending, ERP posting or merging is introduced here.

## Scope and non-goals

Included: the common contracts above, only SDK gaps demonstrably required by these hubs, compatibility fixes and release-bound setup/operation evidence. Domain recipes, retrieval policies, reporting logic and samples remain in the hub repositories. Under B042 the Order Desk owns canonical ERP code and Customer Desk retains a marked, verified read copy. No fourth repository, new shared distribution or replacement agent framework is proposed.

Use maintained runtime SDK facilities first, then libraries, then narrow owned code. Reuse existing channels, operations, approvals, schedules, artifacts, backup, access and data-directory functions. Do not duplicate them inside each hub. SDK changes need their own narrowly scoped PRs and explicit dependency links. The named must-haves are delegated setup versus human confirmation, proposed-change storage and authorized file revision activation, and any demonstrated per-tool/source grant gap. Reuse existing implementations where they satisfy these contracts. No agent merges them automatically. Documentation/configuration defaults must not introduce new required files or fields for existing hubs.

Out of scope: Open WebUI mode, arbitrary new UI applications, universal model/provider parity, autonomous policy promotion, generic ETL, a new memory platform, or new commercial feature gates.

## Delivery and compatibility

Build order is a dependency order, not separate partial releases: resolve common setup/access/source contracts and SDK must-haves, stabilize existing behavior, complete each hub's proposed end-to-end scope, then qualify the intended release. Each hub can be approved independently but cannot bypass its dependencies or completeness gates. Dates and effort commitments follow the approved scope.

Keep existing case IDs, work items, evidence, operation receipts, provider links and shared file revisions. New data/configuration versions have a previewed migration, backup/restore rehearsal and explicit compatibility version. Migration never resends, reposts, re-tags the entire history or generates new irreversible actions. A rollback uses a compatible prior release or restores a verified backup with a documented replay fence, never a silent downgrade against an incompatible schema.

Mutable operational state, caches, imported working data, artifacts and local sample-ERP data follow the SDK-managed data root, including `HUBZOID_DATA_DIR`. Versioned Hub instructions, approved knowledge and configuration retain their existing folder paths and reviewed update mechanism. No new required source layout is introduced. Deployments mounting source read-only use an explicitly qualified builder/update workspace rather than writing through that mount. Validate customer hosting on Railway and Maritime using provider-native packaging and the existing sandbox architecture. For each promoted hub/provider/runtime combination record the SDK/hub versions, secrets, persistence, sign-in/MCP callbacks, teammate access, restart, scheduler behavior, sleep/wake limits, backup/restore and upgrade result. No paid account, resource or real customer connection is provisioned by approving the text alone. Qualification actions must use the subsequently authorized test scope.

### Required qualification table

Proposed for approval: a finite covering table, not the full cross-product of every authoring, runtime, host and connector option. Each hub lists its provider journeys against these six rows. All required rows use real runtime/provider journeys. Local Claude has two separately exercised setup paths. Synthetic contract tests cover remaining permutations and failure conditions but do not establish support for unlisted combinations.

| Row | Host | Sole execution runtime | Setup authoring surface | Evidence |
|---|---|---|---|---|
| L-C | Local | Claude | Claude Code and Cowork, independently | Real own-material journey for each setup surface |
| L-X | Local | Codex | Codex | Real own-material journey |
| R-C | Railway | Claude | Claude Code | Real task, teammate, persistence and scheduling/recovery |
| R-X | Railway | Codex | Codex | Same hosting acceptance |
| M-C | Maritime | Claude | Cowork | Same hosting acceptance, including Cowork capabilities |
| M-X | Maritime | Codex | Codex | Same hosting acceptance |

Customer requires both Zoho and Freshdesk without ERP on every row. Order requires Gmail intake and four ERP-free outputs on every row. Factory requires its real GitHub and sandbox pipeline on every row. Both desks additionally qualify their optional ERPNext paths on every required row. Customer covers scoped factual enrichment for each helpdesk; Order covers drafts, exact approval, submission and recovery. An ERP-free pass does not establish the optional ERP path. This is a covering table for setup surfaces, with every proposed provider feature tested on the selected runtime/host rows. A required row blocked by provider capability stays incomplete and returns for a founder decision.

Each run records exact SDK/hub versions, OS/provider configuration, authoring capabilities, runtime/model/authentication method, provider editions/scopes, costs and limits. Prefer the runtime's existing supported authentication. Unattended/shared subscription use must be demonstrated for that precise row before claiming it. An unsupported auth method is a blocker, not authorization for paid API fallback. Each hosted row also covers sign-in/MCP callbacks, scoped teammate access, restart and custom-data-root persistence, workflows/schedules, sleep/wake, backup/restore and upgrade. No provider or runtime combination is declared supported merely by a synthetic pass.

Use immutable SDK commit pins for development evidence. Promotion requires a tagged SDK release containing the dependencies, with the exact tag and resolved commit recorded. No moving branch is a release prerequisite. Required fixes and all required rows must pass before that hub is complete. No dates, paid test resources or live account changes are authorized by approving proposal text alone.

## Definition of done

- [ ] The three hub proposals reference this exact contract and identify domain code versus SDK ownership.
- [ ] A clean installation completes the supported Claude Code setup with zero manual Hubzoid UI configuration. Cowork's required path is exercised separately with recorded capabilities and handoffs.
- [ ] A serialized setup preview, two repeated applies and an interrupted/resumed setup produce one connection/import/configuration, preserving a later user edit and keeping credentials out of outputs.
- [ ] The builder obtains useful own-material output and proves one saved correction after restart. A teammate repeats appropriate work without setup privileges.
- [ ] Fixed fixtures produce identical authorized rule/source revision identifiers, evidence identifiers, domain decisions and allow/deny outcomes across chat, workflow and MCP. Live retrieval records the actual evidence and policy revision. Delegated hub execution and external-client generation are distinguished. Direct tool/API and artifact requests cannot bypass scopes.
- [ ] Negative access cases cover missing grants, cross-hub/source/customer/repository access, queued-work revocation, external-content instructions and stale approval. Delegated setup/runtime credentials cannot confirm protected acts. Event/service initiators cannot approve. Per-tool decisions appear in a safe audit trail.
- [ ] Every required qualification row and named provider journey passes with genuine end-to-end evidence. Synthetic coverage of other permutations, real-provider runs, skips, timeouts and unavailable combinations are shown separately.
- [ ] All in-scope UI states are finished and tested with real content at desktop/mobile sizes. There are no placeholder features or qualification steps.
- [ ] An independently mounted source folder and custom data root retain one authoritative approved revision through a supported source update, restart and rollback.
- [ ] Operator instructions and tested backups preserve data and deduplication through restart, restore, upgrade and rollback. Critical heavy/slow tests are run explicitly before handoff.

## Decisions requested and remaining questions

Approval would adopt the seven-priority contract, file/CLI/API-first setup with explicit identity/consent/approval handoffs, scoped shared context and the three domain scopes. The concrete recommended decisions are the six-row covering matrix, narrow delegated setup identity with separate human confirmation, personal-owner self-approval where authorized, the single-authority file/SDK split, and a tagged SDK release for promotion. Approval of Customer also includes a narrow in-repo Freshdesk editor integration when required, with verifiable persistence and linked identity. Approval of Order selects a customer-owned Gmail OAuth client and explicit mail minimization. ERP becomes optional for both desks, superseding earlier ERP-first assumptions for these proposals. No new Cowork helper is pre-approved. A missing existing capability returns for a decision. It would authorize implementation planning/build work only after the founder explicitly approves the selected proposal revisions.

Provider draft capabilities, runtime/authoring compatibility and any unavailable access APIs are implementation discovery checks with the observable outcomes above as the requirement. A failed capability check must return for a scope decision rather than silently replacing the user experience or declaring an untested variant supported. No unresolved question authorizes weakening exact approvals or exposing data.
